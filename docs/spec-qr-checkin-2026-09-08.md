# QR受付・回数券・運営会員 仕様書 v1.2

> **この版の位置づけ**：2026-09-08 の相談で決まったことをまとめた版。
> v1.1 で **都度払い1,200円の存続**が決まり、料金を「表」で持つ方式に変えた。
> v1.2 で **回数券3,980円の未収管理**を追加した。
> **実装は1行も書いていない。**「開発してください」の指示待ち。

---

## 1. 背景

- 参加者が増えた。直近2回は **13名・13名**（2026年8月）
- **来月から月4回開催**（昼2回・夜2回）。夜練はすでに開始済み（8/25・9/1・9/8・9/15）
- 現状は管理者が1人ずつ画面でチェックする方式。人数×開催回数で負担が倍になる
- 回数券の残り回数を、**本人も**その場で把握できるようにしたい
- 参加表（通算の記録）と回数券（お金）が二重管理になっている

## 2. 目的

**QRを1枚会場に貼り、各自のスマホで受付してもらう。管理者は1日1回「確定」を押すだけにする。**
その1回の確定で、参加表・回数券・開催回数がすべて正しく更新される状態にする。

## 3. 決定事項（2026-09-08 の相談で確定）

| # | 項目 | 決定 |
|---|---|---|
| 1 | QRの方式 | **会場に1枚の固定QR**。各自のスマホで読む |
| 2 | 本人の特定 | 名簿から名前をタップ。**初回だけ**。以降その端末が覚える |
| 3 | 回数券が減るタイミング | **管理者が確定を押したとき**。受付した瞬間には減らさない |
| 4 | 受付でチェックする項目 | **準備 / 参加 / フォロー** の3つ。複数選択可。受付の1回でまとめて押す |
| 5 | ポイント制 | **なし**（採用しない） |
| 6 | 割引 | **運営会員**は回数券が **2,980円**（1,000円引き）。線引きは実行委員が人間の目で決める |
| 7 | 3項目チェックの用途 | ポイント計算には使わない。**運営会員を決めるときの材料**として集計する |
| 8 | 料金 | 初回体験500円 ／ **都度参加1,200円** ／ 5回券3,980円（運営会員2,980円）。**都度払いは残す**（v1.1で変更） |
| 9 | 体験の扱い | **体験日は無料・回数券を消化しない**。入会した場合、5回は**次回から**まるまる使える |
| 10 | 券が残り0の人 | **都度参加1,200円で参加できる**。券の購入も選べる（v1.1で変更） |
| 13 | 料金の持ち方 | コードに直書きせず**料金表として持つ**。管理画面から金額の変更・種別の追加ができる（v1.1で追加） |
| 14 | 都度払い・体験の現金 | **未収を持たない**。管理者が確定でチェックを入れた時点で「受け取った」とみなす（v1.1で追加） |
| 15 | **回数券3,980円の未収** | **追いかける**。付与するときに「入金済み／未収」を選ぶ。金額が大きく、後払いが起きるため（v1.2で追加） |
| 16 | 未収の見せ方 | 管理画面に出すほか、**本人の受付完了画面にも控えめに出す**。人前ではなく本人のスマホにだけ（v1.2で追加） |
| 17 | 未収のまま参加できるか | **できる**。会場に来ている人を記録で止めない。止めるのは催促のほう（v1.2で追加） |
| 11 | 参加表 | 今回**直す**（年の行・時間帯・壊れた合計数式・会員ID列） |
| 12 | 既存GAS | **触らない**。受付専用のGASを新規に作る |

### 3.1 料金表

**コードに直書きしない。**管理画面の「料金設定」から金額を変えられ、種別を足せる形にする。
料金プランの見直しは2027年4月まで保留になっているので、そのとき私を呼ばずに耕平さんだけで直せることを狙う。

| 種別 | 既定の金額 | 回数券 | 参加できるか |
|---|---|---|---|
| 初回体験 | 500円（その場で入会したら **0円**） | 消化しない | ◯ |
| 都度参加 | 1,200円 | 消化しない | ◯ |
| 回数券で参加 | 0円 | **1回消化** | ◯ |
| 5回券を買う | 3,980円 | 5回付与 | ◯ |
| 5回券を買う（運営会員） | 2,980円 | 5回付与 | ◯ |

**券を持っている人は券が優先。**選択肢が出るのは、券が0の人・持っていない人だけ。

### 3.2 未収の扱い（v1.2）

**その場で受け取る少額（都度1,200円・体験500円）は未収を持たない。回数券3,980円だけ追いかける。**
金額が大きく「次回持ってきます」が現実に起きるため。

| 場面 | 動き |
|---|---|
| 券を付与するとき | ［入金済み］／［🔴 未収］を選ぶ。**金額は料金表から自動**（3,980円 or 運営会員2,980円） |
| 未収のあいだ | メンバーの名前の横に 🔴 **3,980円 未収** が出続ける。**参加は普通にできる** |
| 入金があったら | 未収一覧でチェック → 入金済みに変わり、**入金日が記録される** |
| 本人の画面 | 受付完了の画面に控えめに「回数券のお支払いが未確認です」。人前には出さない |

**データの持ち方**：既存の `purchases[]`（購入記録・37件）に `paid`（入金済みか）と `paidAt`（入金日）を足す。
**`paid` を持たない既存の37件は「入金済み」として扱う**（過去の未収を掘り返さない）。

## 5. データの置き場（4つに分ける）

**参加表と回数券は一致しない。**初回体験が無料で、券を消化しない開催があるため。
一致させようとすると必ず壊れるので、最初から別々に持つ。

| データ | 意味 | 置き場 | 誰が書くか |
|---|---|---|---|
| **参加表** | 立ち上げからの通算の記録。**絶対的に正しい参加回数** | スプレッドシート「参加表」 | 確定時に受付GASが列を立てる |
| **回数券の残り** | お金の管理 | 今まで通り `AppData!A1` の `members[].tickets` | 確定時に管理者の端末から（既存の保存経路） |
| **受付ログ** | 今日誰が来たか・準備/フォローをやったか | 新タブ **「受付ログ」** | 各自のスマホが**1行追記するだけ** |
| **開催回数** | 第◯回 | 参加表の日付列の本数がそのまま回数 | 自動 |

> **なぜ受付ログを別の入れ物にするのか**
> 今の保存方式は「全員分のデータを1個のJSONにして1マスに丸ごと上書き」。
> 各自のスマホが同時に保存すると、後に押した人が前の人の記録を消す。
> 受付だけを**追記専用**の別タブに逃がすことで、上書き事故が原理的に起きなくなる。
> 全体の上書きは今まで通り管理者の端末1台だけが行う。

## 6. 全体の構成

作るものは3つ。既存GASは1行も触らない。

```
【各自のスマホ】          【クラウド】                  【管理者のタブレット】
 会場のQRを読む
   ↓
 checkin.html（新規）
   ↓ 名前タップ
   ↓ 準備/参加/フォロー
   ↓ ［受付する］
   └──POST──→ 受付専用GAS（新規）
                  ↓ 1行追記
              「受付ログ」タブ ──GET──→ index.html（追加）
                                          「今日の受付」一覧
                                              ↓ ［確定］1回
                          ┌───────────────┴────────────┐
                          ↓                                        ↓
              受付GAS が「参加表」に列を立てる          既存の保存経路で
              （開催回数も自動で1増える）              回数券を1つ消化
```

| # | 作るもの | 中身 |
|---|---|---|
| 1 | `checkin.html`（新規1枚） | 各自のスマホが開く受付画面 |
| 2 | 受付専用GAS（新規プロジェクト） | 受付ログへの追記／名簿と当日分の読み出し／参加表への列追加 |
| 3 | `index.html` への追加 | 「今日の受付」パネル・確定ボタン・運営会員フラグ・購入タブの割引・参加合計欄の全員表示 |

## 7. 受付ログ タブの仕様（新規）

1行 = 1人の1回の受付。**追記のみ。既存行は書き換えない**（確定時のK・L列を除く）。

| 列 | 項目 | 内容 |
|---|---|---|
| A | タイムスタンプ | 受付GASがサーバー側で入れる（日本時間） |
| B | 開催日 | `YYYY-MM-DD`。**サーバー側の日本時間**で決める。端末の時計は信用しない |
| C | 時間帯 | 昼 / 夜。受付時刻から自動判定（17時以降なら夜）。確定画面で直せる |
| D | 会員ID | アプリ側のID（`M1774861589770` 形式）。体験の人は空 |
| E | 名前 | 表示用 |
| F | 準備 | TRUE / FALSE |
| G | 参加 | TRUE / FALSE |
| H | フォロー | TRUE / FALSE |
| I | 種別 | 会員 / 体験 |
| J | 支払い種別 | 券 / 都度 / 体験 / 入会（＝体験の日に5回券を買った） |
| K | 状態 | 未確定 / 確定済 / 取消 |
| L | 確定日時 | 確定を押した時刻 |
| M | 金額 | 受付時点の料金表の金額。あとから料金を変えても過去の記録が動かないように、**その時の金額を写しておく** |

**同じ人が同じ日に2回受付した場合**：行は両方残す。**同一「開催日＋会員ID」で最新の行だけを有効**とする。
（消さずに残すのは、後から経緯を追えるようにするため）

## 8. 受付専用GAS の窓口

| 種類 | 窓口 | 中身 |
|---|---|---|
| GET | `?action=roster` | 名簿を返す。`AppData!A1` を**読むだけ**。返すのは `{id, 名前, 残り回数, 券の有無, 運営会員か}` のみ |
| GET | `?action=today&date=YYYY-MM-DD` | その日の受付ログを返す（管理画面用） |
| POST | `{action:'checkin', ...}` | 受付ログに1行追記。**LockService で排他**をかけ、同時アクセスでも行が壊れないようにする |
| POST | `{action:'commit', date, 時間帯, 有効な受付の一覧}` | 受付ログのK列を「確定済」にし、**参加表に列を1本立てて出席チェックを入れる** |

**冪等にする**（同じ操作を2回やっても結果が変わらない）：
`commit` は、参加表に同じ開催日の列が既にあれば**新しく足さずに上書き**する。
通信が切れて確定に失敗しても、もう一度押せば直る形にする。

## 9. checkin.html（参加者の画面）

### 9.1 画面の流れ

```
QRを読む
  ↓
【初回だけ】名簿から自分の名前をタップ
  ↓  ※選んだIDはその端末に保存。次からは「のぶさんですか？→はい」の1タップ
  ↓  ※違う人が使う場合の「別の人に切り替える」も置く
【毎回】 □ 準備（10分前）  □ 参加  □ フォロー   ← 複数チェック可
  ↓
［受付する］
```

### 9.2 受付後の表示（状態で出し分ける）

| 状態 | 表示 |
|---|---|
| 券が2回以上残っている | 受付しました。**回数券 残り3回** |
| 券が残り1回 | 受付しました。**これが最後の1回です。**次の券をご用意ください ／ ［次の券を買う］ |
| 回数券が未収 | 上の表示に加えて、小さく **「回数券のお支払い（3,980円）が未確認です」**（§3.2） |
| 券が残り0 | 回数券がありません。今日の払い方を選んでください<br>［5回券を買う 3,980円］／［今日は都度参加 1,200円］ |
| 名簿にいない | ［はじめての方はこちら］→ 名前を入力 → ［体験のみ 500円］／［今日入会する 3,980円（体験代は無料）］ |

- 残り回数は**確定前の値**を出す。「今日の分を含めると残り2回になります」と一言添える
- 受付は**当日分のみ**受け付ける（開催日でない日は「今日は練習日ではありません」）
- **券が0でも参加できる。**都度参加1,200円を選べばその場で受付が通る。現場で締め出しにならない

## 10. index.html への追加（管理者の画面）

### 10.1 「今日の受付」パネル

```
📋 今日の受付   2026-09-08（夜）        第91回
─────────────────────────────
☑ のぶさん       準備・参加・フォロー    券        残り3回
☑ シンさん       参加                    券        残り1回 ⚠️次の券を
☑ うらさん       参加・フォロー          都度      1,200円
☑ 田中さん(新)   参加                    入会      3,980円  ［入金済み／未収］
☑ ヨネさん       参加                    券        残り2回  🔴3,980円未収
─────────────────────────────
                        本日の受け取り  5,180円
   時間帯［昼／夜］        ［✅ この内容で確定する］
```

- チェックを外した人は確定に含めない（誤タップ・家からの受付をここで止める）
- **チェックを入れて確定する＝お金を受け取った、という意味**。未収という状態は持たない
- 金額は合計だけ出す。入金の記録は今まで通り耕平さんの手作業
- 時間帯は自動判定した値を出し、違っていれば直せる
- 既存の「📅 参加日をまとめて記録する」パネルは**そのまま残す**（QRを使えない人・後日の修正用）

### 10.2 確定を押したときの処理（順番が重要）

1. 受付GASに `commit` を送る → 受付ログを確定済にし、**参加表に列を立てて出席を記録**
2. 成功したら、`members[].tickets` を1つずつ消化する
   - **同じ開催日が既に `tickets` に入っていればスキップ**（二重消化を防ぐ。これで冪等になる）
   - 体験の人・券を持たない人は消化しない
3. 購入希望・入会希望が出ている人を購入タブに送る（**付与そのものは管理者が購入タブで行う**。お金は手作業のまま）
4. 既存の `saveToGAS()` で `AppData!A1` に保存

**1が成功して2以降が失敗した場合**：もう一度確定を押せば直る（1は上書き、2は日付判定でスキップ）。
画面には「確定に失敗しました。もう一度押してください」と出す。

### 10.3 その他の追加

| 追加 | 内容 |
|---|---|
| 参加合計欄 | **全員**の名前を出す。現状は回数券を持つ人（`hasTicket5`）しか表示されない |
| 運営会員フラグ | `members[].isStaff`。管理者が付け外しできる。名前の横に印を出す |
| 購入タブの割引 | 運営会員を選ぶと **2,980円** が初期値になる（通常は3,980円） |
| 準備・フォローの集計 | 受付ログを集計し、人ごとに「準備◯回・フォロー◯回」を出す。**実行委員が運営会員を決めるときの材料** |
| **料金設定** | §3.1の料金表を画面から編集できる。金額の変更・種別の追加。**コードを触らずに料金を変えられる**ようにする |
| **未収の一覧** | 購入タブに置く。誰が・いくら・いつから未収か。合計も出す。チェックを入れると入金済みになり入金日が入る（§3.2） |
| 券の付与 | 付与時に［入金済み／未収］を選ぶ。金額は料金表から自動 |

## 11. 参加表の下ごしらえ（決定事項11）

自動で列を立てる前に、参加表を機械が読める形にする。**作り直しではなく最小限の修理**にとどめる。

| # | 直すこと | 内容 |
|---|---|---|
| 1 | **年の行を足す** | 日付が「9/2」としか入っておらず年がない。年の行を追加する。復元済みの区分（2023年17回／2024年35回／2025年21回／2026年〜）を使う |
| 2 | **時間帯の行を足す** | 昼 / 夜。既存は全部「昼」、8/25以降の夜練を「夜」にする |
| 3 | **会員ID列を足す** | アプリ側のIDと紐づける。名前の表記ゆれ（「木寺のねーやん」↔「木寺ねーちゃん」）で照合が壊れるのを防ぐ。**初回の対応付けは手作業** |
| 4 | **壊れた合計を直す** | 95行目の合計が列ごとに範囲バラバラ。CR列（各人の通算）は10人分の数式が欠落している |
| 5 | **会場の行を整理** | 「テレビ取材」など会場でないものが混ざっている。備考に移す |

**作業前に、耕平さんの手でスプレッドシートの「ファイル → コピーを作成」でバックアップを取る。**
（所有者が別アカウントのため、複製は耕平さんしかできない）

### 11.1 自動で列を立てるときのルール

- 新しい開催日は**右端に1列足す**。年・月・日・時間帯・会場を埋める
- 名簿にいない人（体験）は**行を足す**。会員IDも同時に入れる
- 既に同じ開催日の列があれば足さずに上書き（§8の冪等）

| `AppData` `参加記録` タブの変更 | 触らない |
| 既存GASの改造 | 触らない（回収して読むだけ） |
| 名前の表記ゆれの統一 | §11-3の会員ID列で回避する。統一そのものは別案件 |

## 13. リスクと対応

| リスク | 対応 |
|---|---|
| 各自のスマホが同時に保存して記録が消える | 受付は**追記専用の別タブ**。全体の上書きは管理者の端末1台だけ（§5） |
| 公開URLなので家からでも受付できる | 管理者の確定を通らない限り何も反映されない。確定画面でチェックを外せる |
| 誤タップ・二重受付 | 同一「開催日＋会員ID」は最新の行だけ有効（§7） |
| 確定の途中で通信が切れる | 冪等にする。もう一度押せば直る（§8・§10.2） |
| 会場にWi-Fiがない | 参加者は各自の回線。管理者の確定は帰宅後でもよい |
| 新しいGASが既存GASと衝突する | 着手前に clasp で既存GASを回収し、参照しているシート名を確認する（§4.1） |
| 参加表の修理で既存データを壊す | 着手前に耕平さんがスプレッドシートを複製（§11） |
| 名簿にいない人が受付できず現場で止まる | 「はじめての方」から名前を入力して受付できる（§9.2） |
